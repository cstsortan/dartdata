# Specification: z_pk Integer Foreign Key Resolution

**Track ID:** zpk-integer-fk_20260405
**Type:** Refactor
**Created:** 2026-04-05
**Status:** Draft

## Summary

Make FK columns store `z_pk` integers instead of UUID strings, aligning with CLAUDE.md's requirement ("Foreign keys use `z_pk` integers, not user-facing UUID strings") and real SwiftData schema behavior observed in production `.presentr` bundles.

## Context

The current implementation stores UUID strings in FK columns because `ModelContext` has no mechanism to resolve UUIDs to `z_pk` values. This was a pragmatic workaround — the generator emits `ColumnType.text` FK columns and `toMap()` writes `.id` (UUID string) directly. A real SwiftData database confirms FK columns like `ZSLIDE.ZPRESENTATION` store `Z_PK` integers, not UUID strings.

## User Story

As a dartdata library developer, I want FK columns to store `z_pk` integers so that the schema matches real SwiftData databases and foreign key resolution is consistent with the documented design.

## Acceptance Criteria

- [ ] FK columns in DDL use `ColumnType.integer`, not `ColumnType.text`
- [ ] `toMap()` returns `null` for FK columns (resolution deferred to `ModelContext`)
- [ ] `ModelDescriptor` exposes `getRelationshipIds()` returning FK column -> related UUID map
- [ ] `ModelContext._execute()` resolves FK UUIDs to z_pk integers before INSERT/UPDATE
- [ ] Delete rules (`cascade`, `nullify`, `deny`, `noAction`) resolve parent UUID -> z_pk before querying children
- [ ] `fetchRelated()` resolves parent UUID -> z_pk before querying children
- [ ] Referencing an unsaved parent throws a clear `StateError`
- [ ] Generator emits integer FK columns, null in `toMap()`, and `getRelationshipIds()` override
- [ ] All hand-written test models use object references (not raw FK strings)
- [ ] All existing tests pass with the new integer FK scheme

## Dependencies

- Depends on existing `ModelDescriptor`, `ModelContext`, and relationship infrastructure (all implemented)
- Depends on `z_pk` and `z_opt` system columns being present (implemented)

## Out of Scope

- **Lazy loading / relationship hydration on fetch** — reconstructing related objects from FK z_pk values during `fromMap()`
- **`Z_PRIMARYKEY` metadata table** — dartdata uses SQLite `AUTOINCREMENT`, not a counter table like Core Data
- **`Z_ENT` entity type column** — dartdata doesn't use entity type IDs
- **Junction table FK resolution** — junction tables use a separate mechanism already
- **Parent-before-child insert ordering** — automatic topological sort of pending operations during save; for now, throw a clear error if z_pk lookup fails

## Technical Notes

- Approach: Users set relationships via object references (`Comment(post: myPost)`), never raw FK values. `ModelContext` resolves the related object's UUID to its `z_pk` integer at save time.
- No `REFERENCES` constraint in DDL (matching SwiftData behavior).
- New `getRelationshipIds()` method follows the same pattern as existing `externalFileFields` + `getExternalFile()`.
