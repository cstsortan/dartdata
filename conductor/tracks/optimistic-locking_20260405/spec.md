# Specification: z_opt Optimistic Locking

**Track ID:** optimistic-locking_20260405
**Type:** Feature
**Created:** 2026-04-05
**Status:** Draft

## Summary

Implement optimistic concurrency control using the `z_opt` version counter column. On every UPDATE, `z_opt` is incremented. On save, the library checks that `z_opt` hasn't changed since the object was fetched, detecting concurrent-write conflicts.

## Context

Every model table already has a `z_opt INTEGER NOT NULL DEFAULT 0` column created by `ModelContainer`. However, `ModelContext.save()` does not read, check, or increment this value. This track adds the full optimistic locking lifecycle.

## User Story

As a developer with multiple `ModelContext` instances accessing the same data, I want the library to detect when two contexts try to update the same row simultaneously, so that data corruption from lost updates is prevented.

## Acceptance Criteria

- [ ] `z_opt` is incremented by 1 on every UPDATE (INSERT OR REPLACE with z_opt + 1)
- [ ] Fetched objects carry their `z_opt` value in memory
- [ ] On save, if the row's current `z_opt` differs from the fetched value, throw `OptimisticLockError`
- [ ] `OptimisticLockError` includes the model type, id, expected version, and actual version
- [ ] First write wins — the second concurrent save fails cleanly
- [ ] New tests cover: version increment, conflict detection, conflict-free sequential updates

## Dependencies

- Existing: `z_opt` column in all model tables
- Existing: `ModelContext.save()` with INSERT OR REPLACE

## Out of Scope

- Automatic retry/merge on conflict
- Pessimistic locking (SELECT FOR UPDATE)
- Version history tracking

## Technical Notes

- Store `z_opt` alongside the model data in the context's tracking map (fetched version)
- Change UPDATE from `INSERT OR REPLACE` to a proper `UPDATE ... SET ... WHERE id = ? AND z_opt = ?`
- Check `changes()` result — if 0 rows affected, the version changed; throw `OptimisticLockError`
- INSERT (new rows) always start at `z_opt = 0`, no conflict check needed
- Consider: should `fetchOne`/`fetch` always read z_opt? Yes — it's needed for subsequent saves
