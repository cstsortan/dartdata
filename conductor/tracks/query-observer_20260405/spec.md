# Specification: QueryObserver<T> Widget

**Track ID:** query-observer_20260405
**Type:** Feature
**Created:** 2026-04-05
**Status:** Draft

## Summary

Implement the `QueryObserver<T>` Flutter widget that subscribes to `ModelContext.changes`, re-runs a query when relevant tables are modified, and rebuilds the UI with fresh results.

## Context

The API design document specifies `QueryObserver<T>` as a `StatelessWidget`-like builder pattern that wraps a `Query<T>` and rebuilds when data changes. With Track G providing populated `ContextChangeSet` data, the observer can intelligently filter which saves trigger a re-query.

## User Story

As a Flutter developer, I want to use `QueryObserver<Trip>(query: ..., builder: ...)` in my widget tree and have it automatically rebuild when Trip data changes, so I don't have to manage stream subscriptions manually.

## Acceptance Criteria

- [ ] `QueryObserver<T>` is a `StatefulWidget` with `query` and `builder` parameters
- [ ] `builder` signature: `Widget Function(BuildContext, List<T>? results, Widget? child)`
- [ ] Initial build shows `null` results (loading state), then shows query results
- [ ] After a `save()` that affects the observed table, the query is re-run and widget rebuilds
- [ ] After a `save()` that does NOT affect the observed table, no re-query occurs
- [ ] Disposing the widget cancels the stream subscription
- [ ] Works with the `ModelContext` obtained from `ModelContext.of(context)` or passed directly

## Dependencies

- **Required:** Track G (context-change-set) — populated `ContextChangeSet` with `hasChangesFor(tableName)`
- **Required:** Track I (flutter-providers) — `ModelContext.of(context)` for widget tree access
- Existing: `Query<T>`, `ModelContext.fetch()`, `ModelContext.changes` stream

## Out of Scope

- Pagination within the observer (use `Query.limit/offset` directly)
- Debouncing rapid saves
- Error handling UI (builder receives null on error — consumer handles it)

## Technical Notes

- `initState()`: subscribe to `context.changes`, run initial query
- On change event: check `changeSet.hasChangesFor(descriptor.tableName)` — if true, re-run query
- Use `setState()` to trigger rebuild with new results
- The `child` parameter enables optimization (non-rebuilding subtree)
- Table name resolution: derive from `T` type using the schema's descriptor registry
- Consider: should the observer accept a `ModelContext` directly or always use `.of(context)`? Support both.
