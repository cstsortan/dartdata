# Dart Style Guide

## Formatting

- Use `dart format` (comes with the Dart SDK). All committed code must be formatted.
- Line length: 80 characters (dart format default).
- Use trailing commas in argument/parameter lists when items span multiple lines — this produces cleaner diffs and consistent `dart format` output.

## Naming

| Construct | Convention | Example |
|---|---|---|
| Classes, enums, typedefs | `UpperCamelCase` | `ModelContext`, `DeleteRule` |
| Variables, parameters, fields | `lowerCamelCase` | `primaryKey`, `columnName` |
| Constants | `lowerCamelCase` | `defaultPageSize` |
| Private members | `_lowerCamelCase` | `_database`, `_isOpen` |
| Files | `snake_case.dart` | `model_context.dart` |
| Generated files | `snake_case.g.dart` | `todo.g.dart` |
| Test files | `snake_case_test.dart` | `model_context_test.dart` |

## Libraries and Imports

Order imports as:
1. `dart:` core libraries
2. `package:` third-party packages
3. Relative imports within the library

Separate each group with a blank line. Use `show` / `hide` to be explicit about what is imported when there is ambiguity.

```dart
import 'dart:io';

import 'package:sqlite3/sqlite3.dart';
import 'package:uuid/uuid.dart';

import '../annotations/model.dart';
import '../schema/schema.dart';
```

## Public API

- Every public class, method, and top-level function must have a doc comment (`///`).
- Use `{@template}` / `{@macro}` for shared doc blocks.
- Avoid redundant doc comments that merely restate the name ("Gets the name.").

```dart
/// Opens a SQLite database at [path] and returns a configured [ModelContainer].
///
/// WAL mode and foreign key enforcement are enabled automatically.
/// Throws [StateError] if the schema cannot be applied.
static Future<ModelContainer> open(Schema schema, {String? path}) async { ... }
```

## Null Safety

- Use `late` only when initialization is guaranteed before first use and `null` is not a valid sentinel.
- Prefer `required` named parameters over nullable parameters with a default of `null` when the value is mandatory.
- Never use `!` (null-assertion operator) without a comment explaining why null is impossible at that point.

## Error Handling

- Throw `StateError` for violations of object invariants (e.g., accessing a managed resource after it has been disposed).
- Throw `ArgumentError` for invalid caller-supplied values.
- Never catch-and-swallow exceptions. If you catch, rethrow or handle meaningfully.
- Avoid `dynamic` — always type exceptions explicitly.

```dart
// Good
} on SqliteException catch (e) {
  throw StateError('Failed to open database: ${e.message}');
}

// Bad
} catch (e) {
  // silently ignored
}
```

## Immutability

- Prefer `final` for local variables and fields that are not reassigned.
- Prefer `const` constructors wherever possible.
- Use `List.unmodifiable`, `Map.unmodifiable` for returned collections that callers should not mutate.

## Async

- Use `async`/`await` throughout. Do not mix `.then()` chains with `await` in the same function.
- Methods that perform I/O must be `async` and return `Future<T>`.
- Streams: use `StreamController.broadcast()` for event buses (e.g., `ModelContext.changes`).

## Tests

- Test file mirrors source file: `lib/src/context/model_context.dart` → `test/model_context_test.dart`.
- Each test has a single, clear assertion focus. Prefer many small tests over one large test.
- Use `setUp` / `tearDown` to isolate state between tests (in-memory SQLite or temp directory).
- Test names follow the pattern: `<method> <condition> <expected outcome>`.

```dart
test('fetchOne returns null when no matching record exists', () async { ... });
test('save throws StateError after context is closed', () async { ... });
```

## Code Generation (`.g.dart` files)

- Never edit `.g.dart` files manually — they are regenerated by `build_runner`.
- Generated descriptors expose `QueryField<T>` statics for type-safe predicates.
- Hand-written test models in `test/helpers/test_models.dart` simulate generator output and must stay in sync with the generator's actual output format.

## Sealed Classes

Use sealed classes for state machines. Each subclass represents one state and carries only the data relevant to that state.

```dart
sealed class ExternalFile { ... }
final class _ManagedState extends ExternalFile { ... }
final class _StagedBytesState extends ExternalFile { ... }
```

Exhaustive `switch` expressions on sealed types are preferred over chains of `is` checks.

## Prohibited Patterns

- No `dart:html` or any web-only library.
- No Flutter engine dependencies (`dart:ui`, `package:flutter/*`) in the core `dartdata` library.
- No Dart macros.
- No `sqflite` — use `sqlite3` FFI exclusively.
- No `dynamic` in public API signatures.
