# Specification: Generator — Relationship Emission

**Track ID:** generator-relationships_20260405
**Type:** Feature
**Created:** 2026-04-05
**Status:** Draft

## Summary

Extend the code generator to detect `@relationship` fields, emit foreign key columns for to-one relationships, generate hidden junction tables for simple many-to-many relationships, and populate `RelationshipDefinition` entries in the generated descriptor.

## Context

The generator currently returns `relationships => []` (TODO at line ~57 in `model_generator.dart`). The hand-written test models define `RelationshipDefinition` entries manually. This track makes the generator produce them automatically from `@relationship` annotations.

## User Story

As a developer, I want to declare `@relationship(deleteRule: DeleteRule.cascade) List<BucketListItem> bucketList` on my model and have the generator automatically create the FK column on `BucketListItem` and emit the correct `RelationshipDefinition`, so relationships work without hand-written descriptors.

## Acceptance Criteria

- [ ] To-one (`RelatedModel?` / `RelatedModel`): generator emits FK column (`relatedModel_id INTEGER REFERENCES related_model(z_pk)`) on the owning table
- [ ] To-many (`List<RelatedModel>`): generator emits FK column on the child table (not the parent)
- [ ] `@relationship(inverse: 'fieldName')` wires inverse relationships correctly
- [ ] `@relationship(deleteRule: ...)` is stored in the generated `RelationshipDefinition`
- [ ] Simple many-to-many (both sides `List<T>`): generator emits a hidden junction table with two FK columns
- [ ] Explicit junction model (many-to-many with extra fields): no junction table generated
- [ ] Generated `RelationshipDefinition` includes `fieldName`, `relatedTable`, `cardinality`, `inverseFieldName`, `deleteRule`

## Dependencies

- Existing: `@relationship` annotation class
- Existing: `RelationshipDefinition`, `RelationshipCardinality` in schema

- Existing: hand-written test models demonstrate expected output format

## Out of Scope

- Runtime enforcement of delete rules (Track A)
- Relationship fetching/lazy loading (Track A)
- Complex relationship validation (circular references, etc.)

## Technical Notes

- Cardinality inference: `List<T>` → toMany, `T?` → toOne (optional), `T` → toOne (required)
- FK column naming: `<fieldName>_id` (snake_case) referencing `z_pk` on the related table
- Junction table naming: `_<table_a>_<table_b>` (alphabetical order, underscore prefix)
- The `inverse` parameter helps the generator match both sides of a relationship
- For many-to-many detection: both sides have `List<OtherModel>` with `@relationship` — one side has `inverse`
- Use `element.type` to resolve the related model class name and derive the table name
