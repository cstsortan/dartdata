# Specification: Error Handling & Edge Cases

**Track ID:** error-handling_20260405
**Type:** Feature
**Created:** 2026-04-05
**Status:** Draft

## Summary

Harden the library with proper error handling for edge cases: read-only mode enforcement, multiple concurrent contexts, disposed container detection, and graceful handling of corrupt or missing database files.

## Context

The library works well for the happy path but lacks guards for misuse and failure scenarios. `isReadOnly` is accepted but not enforced, `dispose()` doesn't exist yet (Track I adds a basic version), and there's no protection against using a disposed container.

## User Story

As a developer, I want clear, descriptive errors when I misuse the API (e.g., writing to a read-only container or using a disposed context), so that bugs are caught early with actionable messages.

## Acceptance Criteria

- [ ] `isReadOnly: true` prevents insert, delete, and save operations; throws `StateError`
- [ ] Using a disposed `ModelContainer` or `ModelContext` throws `StateError` with "disposed" in the message
- [ ] Multiple `ModelContext` instances on the same container work correctly for reads
- [ ] Concurrent saves from multiple contexts are serialized by SQLite (no corruption)
- [ ] Opening a corrupt database file throws a descriptive error (not a raw SQLite error)
- [ ] Opening a non-existent path creates the database (standard mode) or throws (document mode, missing directory parent)

## Dependencies

- Depends on: Track I (flutter-providers) for `dispose()` implementation
- Existing: `ModelContainer`, `ModelContext`, all CRUD operations

## Out of Scope

- Automatic recovery from corruption
- Database file repair utilities
- Write-ahead log recovery (SQLite handles this internally)

## Technical Notes

- `isReadOnly`: check in `ModelContext.insert()`, `delete()`, `save()` — throw early
- Disposed state: add `bool _disposed = false` flag to container and context; check at entry to every public method
- Multiple contexts: should work naturally since SQLite handles locking; write tests to confirm
- Corrupt DB: catch `SqliteException` during open and wrap in a `DatabaseCorruptionError`
- Consider: should `ModelContext` hold a weak reference to its container to detect disposal?
